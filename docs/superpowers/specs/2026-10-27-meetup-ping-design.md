# คนส. CoNnextS — "ชวนเจอ & ส่งสัญญาณหากัน" (Meetup Ping) Design Spec

วันที่: 2026-10-27 · branch: `feature/meetup-ping` · สถานะ: รอเจ้าของตรวจ

## 1. เป้าหมาย

- กดขอเชื่อมต่อแล้ว **เครื่องอีกฝ่ายรู้ทันที** (เสียง + การ์ด) ภายในไม่กี่วินาทีเมื่อเปิดแอปอยู่
- เมื่อ**ทั้งสองฝ่ายตกลง**แล้ว เดินหากันในระยะใกล้ (~10–20 เมตร) โดยชูมือถือที่เป็น**สีและสัญลักษณ์เดียวกัน** และกด "ส่งสัญญาณ" ให้อีกเครื่องเต้นและดัง
- เกณฑ์สำเร็จ: คำชวนถึงอีกเครื่องภายใน ≤ 5 วินาที (เปิดแอปอยู่) และ ≤ 20 วินาที (กรณีพึ่งทางสำรอง); ทั้งสองจอแสดงสี+สัญลักษณ์ชุดเดียวกันเสมอ

สิ่งที่เจ้าของเลือก: ต้องตอบรับก่อนจึงส่งสัญญาณได้ (A) · คำชวนเกิดทั้งตอนกดเชื่อมต่อและชวนซ้ำได้ทุกเมื่อ (A) · คำชวนบันทึกในตาราง + สัญญาณผ่านช่องสด (C) · อนุมัติเพิ่มตาราง `meetups`

สิ่งที่สันนิษฐาน: ใช้ได้เฉพาะตอนเปิดแอปอยู่ (ไม่มี push ตอนปิดจอในรอบนี้); ไม่มีการบอกตำแหน่ง/ระยะทาง

ไม่อยู่ในขอบเขต: push notification ตอนปิดจอ/ล็อกเครื่อง, Bluetooth/UWB/GPS/ตำแหน่งในอาคาร, Street View 360°, หลังบ้าน `/admin`, การแก้ตาราง/นโยบายเดิม

## 2. ลำดับการใช้งาน

### คำชวนเกิดได้ 2 ทาง
1. **อัตโนมัติ** — หลัง `connect(ก → ข)` สำเร็จ (ยืนยันจากฐานข้อมูลแล้ว) สร้างคำชวนให้ทันที
2. **ชวนซ้ำ** — ปุ่ม "ชวนเจอกันตอนนี้" บนแถวของคู่ใน `/commitments` และบนหน้า `/connection/$id`; กดได้เมื่อคู่นั้นไม่มีคำชวนที่ `pending`/`accepted` ที่ยังไม่หมดอายุ

### ฝั่งผู้รับ (ข)
- เปิดแอปอยู่: เสียงสั้น 2 โน้ต (+ สั่นถ้าเครื่องรองรับ) และ**การ์ดคำชวน**ด้านบนจอ: รูปแทนตัว · "**{ชื่อ ก} อยากเจอคุณตอนนี้**" · เหตุผลแมตช์ 1 บรรทัด · ปุ่ม "ตกลง เจอกันเลย" / "ไว้ทีหลัง"
- ไม่ได้เปิดแอป: เปิดแอปภายใน 30 นาทีจากเวลาชวน ยังเห็นการ์ดคำชวนที่ค้าง; เลยกำหนดถือว่าหมดอายุ (ไม่แสดง)
- "ไว้ทีหลัง" → สถานะ `declined` ผู้ชวน**ไม่ได้รับแจ้ง** การ์ดปิดเงียบ ๆ
- "ตกลง เจอกันเลย" → สถานะ `accepted` แล้วเข้า**โหมดหากัน**ทันที

### ฝั่งผู้ชวน (ก)
- หน้าฉลองเดิมเพิ่มบรรทัด "ส่งคำชวนเจอแล้ว รอ {ชื่อ ข} ตอบ"
- เมื่อ ข ตกลง: เสียง + การ์ด "**{ชื่อ ข} พร้อมเจอแล้ว!**" ปุ่ม "เริ่มหากัน" (และ "ไว้ทีหลัง" ปิดการ์ด — ยังเข้าโหมดได้จากหน้าคู่จนหมดอายุ)

### โหมดหากัน (เต็มจอ ทั้งสองคน)
- พื้นจอเป็นสีของคู่ + สัญลักษณ์สีขาวใหญ่ตรงกลาง + รูปแทนตัวและชื่ออีกฝ่าย + "ชูมือถือขึ้น มองหาจอ{ชื่อสี}กับรูป{ชื่อสัญลักษณ์}"
- "ส่งสัญญาณ" — จอทั้งสองเต้นแรง 2 ครั้ง + เครื่องอีกฝ่ายดัง; เว้นระยะกดขั้นต่ำ 2 วินาที
- "เจอกันแล้ว!" — สถานะ `done` ปิดโหมดทั้งสองเครื่อง แล้วพาไป `/connection/$id`
- "ออก" — ปิดโหมดของตัวเอง (คำชวนยังเป็น `accepted` จนหมดอายุ เข้าใหม่ได้จากหน้าคู่); หมดอายุครบ 30 นาทีหลังสร้างคำชวน ปิดเอง
- ระหว่างอยู่ในโหมด ขอไม่ให้จอดับ (Screen Wake Lock ถ้ามี) ปล่อยเมื่อออก

## 3. ข้อมูลและสิทธิ์

### ตารางใหม่ `public.meetups` (migration ใหม่ใน `supabase/migrations/`)

| คอลัมน์ | ชนิด | หมายเหตุ |
| --- | --- | --- |
| `id` | uuid PK default `gen_random_uuid()` | |
| `connection_id` | uuid NOT NULL → `connections(id)` ON DELETE CASCADE | |
| `inviter` | uuid NOT NULL → `participants(id)` | |
| `invitee` | uuid NOT NULL → `participants(id)` | ต้องเป็นอีกฝ่ายของ connection |
| `status` | text NOT NULL default `'pending'` CHECK in (`pending`,`accepted`,`declined`,`done`,`cancelled`) | |
| `signal_key` | uuid NOT NULL default `gen_random_uuid()` | |
| `created_at` | timestamptz NOT NULL default `now()` | |
| `responded_at` | timestamptz NULL | |
| `expires_at` | timestamptz NOT NULL default `now() + interval '30 minutes'` | |

- Unique partial index: 1 แถวต่อ `connection_id` ที่ `status in ('pending','accepted')`
- Trigger `BEFORE INSERT` (ฟังก์ชัน `SECURITY DEFINER` ใน schema `private`):
  1. ยืนยันว่า `{inviter, invitee}` = `{user_a, user_b}` ของ connection (ไม่ตรง → raise exception)
  2. เปลี่ยนแถวของ connection เดียวกันที่ `status in ('pending','accepted') AND expires_at <= now()` เป็น `cancelled` ก่อน — คำชวนที่หมดอายุจึงไม่บล็อกคำชวนใหม่
- CHECK `inviter <> invitee`
- เพิ่มใน publication `supabase_realtime` เหมือนตารางอื่น (เผื่อใช้ได้) แต่**ไม่พึ่ง**การส่งสดของตารางนี้

### นโยบาย RLS (ใช้ `private.is_my_connection` / `private.is_my_participant` เดิม)
- SELECT: `private.is_my_connection(connection_id)`
- INSERT: `private.is_my_connection(connection_id) AND private.is_my_participant(inviter)`
- UPDATE: `private.is_my_connection(connection_id)` และเปลี่ยนสถานะได้ตามกติกา:
  - `pending → accepted | declined` เฉพาะ `invitee`
  - `pending → cancelled` เฉพาะ `inviter`
  - `accepted → done | cancelled` ทั้งสองฝ่าย
  - ช่องอื่นแก้ไม่ได้ (บังคับด้วย trigger `BEFORE UPDATE`)
- DELETE: ไม่อนุญาต

### การส่งสัญญาณ (Supabase Realtime Broadcast)
- **กริ่งเคาะประตู** — ทุกเครื่องที่มีโปรไฟล์ subscribe ช่อง `inbox:<my participant id>`; หลัง insert/update คำชวน ฝ่ายที่เปลี่ยนส่ง broadcast `{ type: "knock" }` (ไม่มีข้อมูลอื่น) ไปยังช่องของอีกฝ่าย → ผู้รับดึง `meetups` ที่เกี่ยวกับตัวเองผ่าน RLS ปกติ
- **ทางสำรอง** — ขณะแอปมองเห็นอยู่ ดึง `meetups` ทุก ~20 วินาที และทุกครั้งที่ `visibilitychange` → visible
- **ช่องหากัน** — ทั้งสองเข้าช่อง `meet:<signal_key>` (อ่าน `signal_key` ได้เฉพาะคนในคู่) ส่ง broadcast `{ type: "ping", from: <sender participant id> }`; ไม่เขียนฐานข้อมูล
- ความเสี่ยงที่ต้องยืนยันก่อน (งานแรกของแผน): การส่งสด postgres_changes อาจไม่ผ่าน RLS ที่ใช้ header `x-device-id` — ดีไซน์นี้ไม่พึ่งมัน; ยืนยันว่า Broadcast ใช้ได้กับ anon key ของโปรเจกต์ (ถ้าไม่ได้ ใช้ทางสำรองอย่างเดียวและแจ้งเจ้าของ)

### สีและสัญลักษณ์ของคู่
- `pairBadge(signalKey: string) → { color: BlockColor; symbol: PairSymbol }` คำนวณแบบ deterministic จาก hash ของ `signal_key`
- 6 สีจาก `BLOCK_TAG` (คู่สีที่ผ่าน 4.5:1 แล้ว) × 6 สัญลักษณ์: ดาว · หัวใจ · วงกลม · สามเหลี่ยม · สี่เหลี่ยม · กังหัน = 36 ชุด
- ชื่อสีและสัญลักษณ์ภาษาไทยสำหรับข้อความ "มองหาจอ…"

### ผลกระทบต่อของเดิม
- `store.connect` เมื่อสำเร็จเรียก `createMeetup(connectionId)`; ถ้าล้มเหลว การเชื่อมต่อยังอยู่ แสดง toast "ยังส่งคำชวนเจอไม่สำเร็จ กดชวนใหม่ได้"
- ไม่แก้ตาราง/นโยบายเดิม ไม่แตะ `/admin`
- โหมด dev `?dryrun` ห้ามเขียน `meetups` (จำลองในเครื่อง)

## 4. หน้าตา เสียง และการเข้าถึง

- การ์ดคำชวน/ตอบรับ: การ์ดขาวมุมมน, รูปแทนตัว 56px, หัวข้อ 22px, ปุ่ม ≥ 56px; ประกาศแบบ `aria-live="polite"` ไม่ขโมยโฟกัส; หลายคำชวนแสดงทีละใบ + "อีก N คำชวน"; แสดงทุกหน้าผู้เข้าร่วม (ไม่แสดงใน `/admin`)
- โหมดหากัน: dialog เต็มจอ (focus trap, Esc = ออก, คืนโฟกัส); สัญลักษณ์ ~40% ความกว้างจอ; ข้อความ ≥ 20px; ตัวหนังสือบนพื้นสีใช้คู่สีจาก `BLOCK_TAG`
- การเคลื่อนไหว: เต้นความสว่างช้า ~1 ครั้ง/วินาที; ส่ง/รับสัญญาณ = เต้นแรง 2 ครั้ง; **ไม่เกิน 3 ครั้ง/วินาที** ทุกกรณี; `prefers-reduced-motion` = สีนิ่ง + กรอบหนาชั่วครู่แทน
- เสียง: ใช้ระบบเสียงเดิม (`src/lib/notify.ts` — `playConnext`, `unlockAudio`, `isSoundOn`); เคารพการปิดเสียงในหน้าแจ้งเตือน; ปลดล็อกเสียงตอนแตะครั้งแรก; เล่นไม่ได้ก็ยังแสดงการ์ด
- สั่น: `navigator.vibrate` เมื่อรองรับเท่านั้น
- ความเป็นส่วนตัว: broadcast ไม่มีชื่อ/ตำแหน่ง/ข้อมูลส่วนตัว; ไม่มีการบอกระยะหรือตำแหน่ง

## 5. การจัดการข้อผิดพลาด

- สร้างคำชวนไม่สำเร็จ → toast + ปุ่ม "ชวนเจอกันตอนนี้" ยังกดได้
- ตอบรับไม่สำเร็จ (เน็ตหลุด/หมดอายุ) → ข้อความในการ์ด "ตอบไม่สำเร็จ ลองอีกครั้ง" หรือ "คำชวนนี้หมดเวลาแล้ว"
- ช่องสดหลุดระหว่างหากัน → แถบเล็ก "สัญญาณขาดหาย กำลังต่อใหม่…" และพยายามต่อใหม่อัตโนมัติ; ปุ่ม "ส่งสัญญาณ" ยังกดได้ (ส่งเมื่อต่อได้)
- หมดอายุระหว่างอยู่ในโหมด → ปิดโหมดพร้อมข้อความ "หมดเวลาหากันแล้ว ชวนใหม่ได้จากหน้าคู่"

## 6. การตรวจ

- Vitest: `pairBadge` (deterministic, กระจายครบ 36 ชุด, ทุกสีผ่าน 4.5:1), กติกาเปลี่ยนสถานะคำชวน (ใครทำอะไรได้ + หมดอายุ), ตัวเว้นระยะส่งสัญญาณ 2 วินาที, การเลือกคำชวนที่จะแสดง (ค้าง/หมดอายุ/หลายรายการ)
- ทดสอบบนเบราว์เซอร์: สองแท็บจำลองสองผู้ใช้ด้วยข้อมูลในเครื่อง (ไม่เขียนฐานข้อมูลจริง) ไล่ ชวน → ตกลง → หากัน → ส่งสัญญาณ → เจอกันแล้ว ที่ 375px และ reduced motion; สแกนตัวหนังสือ ≥ 20px
- Migration: ส่งให้เจ้าของตรวจ ทดสอบ RLS บน Lovable preview หรือโปรเจกต์ทดสอบก่อนใช้จริง; ห้ามรันกับ production จากเครื่องนี้
- แนะนำ: ทดสอบสองเครื่องจริง (iPhone + Android) ก่อนวันงาน
- ทำบน branch `feature/meetup-ping` ไม่ push main จนเจ้าของอนุมัติ
